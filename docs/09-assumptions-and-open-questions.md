## 2. 各項目の詳細

### A-01

**決定**: MVP に Stage 2（2 隻・嵐）と簡易エンジニアパネルを含める（✅ 仮決めのまま）

- 企画書 §14 では「船の複数運行」「嵐・故障イベント」「エンジニアモード」は「余裕があれば」だが、§13 のデモ台本は「嵐で遮断 → 別の船で復旧 → 新しい代表 → エンジニア画面で種明かし」で構成されている。デモを成立させるため、この 3 つの最小限を P0 に前倒しした
- Stage 1 は「3 島・1 隻」のまま、チュートリアルとして使う
- 変更箇所: 要件 §3、進行表 §1、実装計画 M2・M5

### A-02

**決定**: インフラは Cloudflare。操作は Cloudflare CLI（`cf`）を使う（🔁 AWS から変更）

- オーナーの判断で Cloudflare を採用。CLI は Wrangler ではなく、2026-09-28 にベータ版になった次世代 CLI の `cf`（npm パッケージ `cf`）を使う
- 構成: Workers（画面の配信と振り分け）＋ Durable Objects（1 ゲームに 1 つ）＋ Containers（Go サーバー）＋ R2（リプレイの共有、P1）
- 変更箇所: ADR-0016（ADR-0011 を置き換え）、アーキテクチャ §5、DesignDoc §12、実装計画 M6

### A-03

**決定**: シミュレーションはサーバーで実行する。1 ゲーム＝1 Durable Object＝1 コンテナ（✅ 仮決めのまま＋補足）

- オーナーの指定（バックエンドは Go）に沿い、Go のシミュレーションを Cloudflare Containers で動かす
- **補足（決定）**: ゲームを始めるたびにそのゲーム専用のコンテナを起動し、ラウンドが終わったら止める。起動待ちは、ステージ選択の時点でコンテナを起動し始め、ステージ紹介と開会式の演出の間に隠す
- 検討した代替案: 全ゲームで 1 つのコンテナを共有する（起動待ちは最初だけだが、Cloudflare の想定外の使い方になり、再起動で全ゲームが切れる）
- シミュレーションのコアは I/O なしの純粋なライブラリにしてあるので、将来 WASM でブラウザ実行に移すこともできる
- 変更箇所: ADR-0009、ADR-0016、アーキテクチャ §2・§5

### A-04

**決定**: etcd-io/raft v3.7.0（Go 1.26）＋乱数を注入する最小パッチ（✅ 仮決めのまま）

- `etcd-io/raft` は選挙タイムアウトの乱数に `crypto/rand` を使っており、そのままでは「同じシードで同じ結果」（企画書 §15-6）が実現できない。アルゴリズムには触れず、乱数源だけを注入できるようにする 1 か所のパッチを当てる（事前の検証済み。ADR-0005）
- 変更箇所: ADR-0005、`server/third_party/etcd-raft`

### A-05

**決定**: 舞台は次のとおり（🔁 実データを見て変更）

| ステージ | 舞台 | 島（人口は令和 8 年 4 月 1 日基準） | このステージで使うデータ |
|---|---|---|---|
| Stage 1 | 瀬戸内（香川県） | 小豆島（25,881・2 町の合計）、豊島（768）、直島（3,071） | 計画書の航路の距離・所要時間・便数 → 航行時間を**データから決める** |
| Stage 2 | 五島列島（長崎県） | 福江島（31,945）、奈留島（1,927）、中通島（16,112） | 人口の差、計画書の「台風等の自然災害」「世界遺産」の記述 |
| Stage 3 | 伊豆諸島（東京都） | 大島（7,102）、利島（327）、新島（1,967）、神津島（1,855）、三宅島（2,273） | 計画書の**欠航率**（利島 17%）と台風の被害の記録 → 欠航・嵐を**データから決める** |
| Stage 4 | 全国 | 佐渡島（51,492）、利尻島（4,462・2 町の合計）、島後（13,433）、八丈島（7,042）、直島（3,071）、対馬島（28,374）、福江島（31,945） | 人口の大きな差（10 倍以上）による負荷の偏り |
| デモ | 五島版・伊豆版の 2 つ | 五島版: Stage 2 と同じ 3 島 / 伊豆版: 大島・新島・神津島 | どちらでデモをするかは、完成後に決める |

- 選定の基準: 提供された 3 つのデータ（離島振興対策実施地域一覧・離島振興計画書・離島活性化交付金等事業計画書）のすべてに載っている島から、一般に知られている島を優先した
- データの確認でわかったこと:
  - 振興計画書は 26 地域分しかなく、地域ごとに情報量の差が大きい
  - 小豆島地域は航路の距離・所要時間・便数が最も具体的に書かれている
  - 伊豆諸島は島ごとの欠航率がある
  - 長崎県の記述は短く（海上交通 36 字）、五島の航路は創作になる
- Stage 3 は、欠航率をデータとして使うため、欠航率が載っている利島を入れた（八丈島は Stage 4 に残した）
- 変更箇所: データ仕様 §3、ステージ定義、進行表

### A-06

**決定**: 時間の既定値は仮決めのまま。所要時間がデータにある航路は換算して決める（✅＋追加）

| 項目 | 値 |
|---|---|
| ゲーム内時間 | 実時間 1 秒＝ゲーム内 1 秒（1 倍速のとき） |
| Raft の tick | 0.5 秒ごと |
| 定期便（Heartbeat） | 1 秒ごと |
| 航行時間 | 4〜13 秒 |
| 停泊時間 | 1.5 秒 |

- **追加**: 所要時間が計画書に載っている航路（Stage 1 の瀬戸内）は、「実際の所要時間 1 分＝ゲーム内 0.15 秒」で換算する（出典区分 `derived`）。載っていない航路は創作の値（`creative`）
- 変更箇所: データ仕様 §4、ステージ定義

### A-07

**決定**: 選挙タイムアウトは次のとおり（🔁 Stage 1 を変更）

| ステージ | 選挙タイムアウト | ねらい |
|---|---|---|
| Stage 1 | 60〜120 秒（`electionTick: 120`） | 長めにしておき、チュートリアルの終盤で「島を放置しすぎると立候補の相談が始まる」を軽く見せる（チュートリアル T9） |
| Stage 2 以降 | 20〜40 秒（`electionTick: 40`） | 定期便が途切れると選挙が始まることを体験させる |
| デモ | 8〜16 秒（`electionTick: 16`） | 圧縮した時間に合わせる |

- 調整の目安: 選挙タイムアウトは「代表と最も近い島の往復時間」の 2 倍以上にする。ボットで探索してから、人がプレイして決める
- 変更箇所: ステージ定義、進行表 §3・§7

### A-08

**決定**: PreVote と CheckQuorum を有効にする（✅ 仮決めのまま）

- CheckQuorum: 孤立した代表が自分から退くので、嵐のデモが分かりやすい
- PreVote: 孤立していた島が戻ったときに、Term を上げて今の代表を引きずり下ろすのを防ぐ（「手紙を届けたら混乱した」という理不尽を防ぐ）
- ステージ定義で切り替えられるようにし、自由実験モード（P2）では無効にして違いを観察できるようにする
- 変更箇所: ADR-0007、ステージ定義の `raft`

### A-09

**決定**: 住民の依頼は「依頼書」としてゲーム側で代表へ転送する（✅ 仮決めのまま）

- Raft 標準の転送は、代表が分からないときに黙って捨てられる。どのみちアプリ側で再送と重複の排除が必要なので、転送ごと「依頼書」として見える化した
- 変更箇所: ADR-0008、DesignDoc §8

### A-10

**決定**: 依頼の成功は依頼元の島の台帳に適用された時点（✅ 仮決めのまま）

- Commit の時点で成功にすると、「代表と近い島だけで Commit を回す」運航が最適になってしまう（企画書 §7 が避けたいこと）
- 画面では「共和国で確定」（Commit 済み）と「確定」（依頼元に届いた）の 2 段階を見せる
- 変更箇所: ADR-0015、ゲームデザイン §4.3・§5

### A-11

**決定**: スコアの配点は仮決めのまま（✅）

- 通常 100 / 重要 300 / 期限後 30 / 予約失敗 0 / 期限切れ −50 / 航行 2 秒ごとに −1 / 公平ボーナス 5 × 満足度の最小値（最大 500）
- 公平ボーナスを「最小値」にしたのは、1 つの島を見捨てる戦略を明確に不利にするため
- ボットとプレイテストで微調整する
- 変更箇所: ゲームデザイン §5、ステージ定義の `scoring`

### A-12

**決定**: 港キューの規則は仮決めのまま。処分・差し替えをアニメーションで見せる（🔁 演出を追加）

- 規則: 同じ相手への同じ種類の手紙は新しいもので差し替える。「記録して！」は相手ごとに 4 通、Raft の手紙は港全体で 24 通まで。依頼書は再送で置き換える
- **追加**: 処分された手紙は港から「海に流れていく」アニメーションで消え、差し替えられた手紙は入れ替わる様子が分かるようにする。手紙が勝手に消えたと感じさせないため、この演出（FR-MAIL-04）を **P1 から P0 に上げた**
- 変更箇所: ADR-0006、要件 FR-MAIL-04、ゲームデザイン §2.3

### A-13

**決定**: 手紙は全種類を見せ、色と形で 4 系統（定期便・記録・選挙・依頼書）にまとめる（✅ 仮決めのまま）

- 企画書の核は「本物の Raft が出力したメッセージをそのまま運ぶ」こと。Heartbeat の返事・PreVote・記録の拒否なども実際に流れるので隠さない
- 変更箇所: ゲームデザイン §2

### A-14

**決定**: 開会式あり（✅ 仮決めのまま）

- 全ステージで、指定した島に立候補させ（`Campaign()`）、最初の選挙だけは即時に配達して済ませる。当選するかは Raft の投票で決まる
- 変更箇所: DesignDoc §5.3

### A-15

**決定**: 一時停止をいつでも許可する（✅ 仮決めのまま）

- 配送パズルとして考える時間を持てることを優先する。通信が切れたときと、Stage 1 でチュートリアルの案内が出ているときは自動で一時停止する
- 変更箇所: 要件 FR-GAME-04

### A-16

**決定**: ★2 は「重要な資源（花火）がすべて確定」（✅ 仮決めのまま）

- 花火の取り合い（片方が必ず予約失敗になる）と、★2 が達成できることを両立させるため
- 変更箇所: ゲームデザイン §4.1・§5.3

### A-17

**決定**: デモ専用ステージと、発表者が起こす嵐。早送りを MVP に含める（✅＋追加）

- デモ専用ステージ: 五島版（`demo-goto`）と伊豆版（`demo-izu`）。制限時間 120 秒、航行時間は通常の約 0.6 倍、選挙タイムアウト 8〜16 秒、★2 を達成した時点で花火大会へ
- 嵐は発表者がキーで起こす。シードを固定し、ボットで台本どおりに進むことを事前に確かめる。保険として、ノート PC で起動する手順と、リプレイを用意する
- **追加（早送り）**: 速度の切り替え（FR-GAME-05）を **P1 から P0 に上げた**。ゲーム内時間を基準にしているので、早送りしても結果は変わらない

| 対象 | 使える操作 |
|---|---|
| 一般のプレイヤー | 0.5 倍・1 倍・2 倍・4 倍の切り替え、一時停止 |
| デモ用（デモ操作が有効なときだけ） | F キーを押している間 4 倍（Shift で 8 倍）、N キーで「次の到着・出来事まで進めて止まる」 |

- 変更箇所: 要件 FR-GAME-05・FR-EVT-07、プロトコル仕様 §4、DesignDoc §12.2、進行表 §8

### A-18

**決定**: 操作の記録を Durable Object に保存し、リプレイの共有に R2 を使う（🔁 永続化なしから変更）

| 対象 | 保存先 | 時期 |
|---|---|---|
| 操作の記録（ステージ・シード・時刻付きの操作列）とセッションの情報 | Durable Object の SQLite の保存領域 | MVP（P0） |
| リプレイの共有 | Cloudflare R2 | MVP の後（P1） |
| Raft の記録 | メモリ（`MemoryStorage`）のまま。ログのコンパクションもしない | — |

- コンテナが止まっても、同じシードと操作の記録からゲームの状態を再計算して元に戻せる（A-04 の決定性による）
- リプレイは、ブラウザを閉じた後でもサーバーから取り出せる
- 変更箇所: ADR-0017（ADR-0012 を置き換え）、DesignDoc §10・§12、プロトコル仕様

### A-19

**決定**: フロントエンドは React 19 + TypeScript / PixiJS v8 / zustand / dnd-kit / Vite・Vitest・Playwright / pnpm（✅ 仮決めのまま）

- PixiJS は React のラッパーを使わず、React の外で命令的に使い、描画と React の再描画を分ける
- 変更箇所: ADR-0010

### A-20

**決定**: モノレポ・JSON・Go の構造体を正本として `tygo` で TS の型を生成（✅ 仮決めのまま）

- Cloudflare の Worker と Durable Object（TypeScript）も、生成した型を使う
- 変更箇所: ADR-0014、プロトコル仕様

### A-21

**決定**: オープンデータはビルド時の ETL で取り込む（✅＋実データを反映）

- 元データ（CSV）を `data/raw/` にコミットする。利用規約が政府標準利用規約（第 2.0 版）で、出典を書けば再配布できるため
- 振興計画書も CSV なので、文章は ETL で機械的に取り込む。人手の作業は、所要時間の抜き出し（どの地域のどの項目から取ったかを記録する）と、使う文章の選定だけ
- 人口は最新の基準日（令和 8 年 4 月 1 日）の値を使い、複数の自治体にまたがる島は合計する（`derived`）
- 変更箇所: ADR-0013、データ仕様

### A-22

**決定**: インフラの構成は `cf` だけで管理する（🔁 Terraform から変更）

- `cloudflare.config.ts`（TypeScript の設定ファイル）に Worker・Durable Object・コンテナ・R2・ドメインを書き、`cf build` と `cf deploy` で反映する。R2 などの資源は `cf deploy` が自動で作る
- ベータ版の注意点:
  - コマンド・設定・ビルド結果の形式が正式版の前に変わり得るので、`cf` の版を固定する
  - リアルタイムのログ表示は未対応 → ログを保存してダッシュボードで見る
  - シークレットを 1 つずつ登録する機能は未対応 → `cf deploy --secrets-file` でまとめて渡す
  - Durable Object に紐付けたコンテナはプレビュー環境に非対応 → PR では `--dry-run` のみ
- 未確認（M0 で確認する）: 手元でコンテナを動かすのに Docker が必要か、`cf dev` でコンテナまで動くか、コンテナの CPU アーキテクチャ
- 変更箇所: ADR-0016、アーキテクチャ §5、実装計画 M6、`.github/workflows/`

### A-23

**決定**: 日本語のみ・PC ブラウザのみ・匿名（✅ 仮決めのまま）

- 文言はキーで管理し、後で翻訳できるようにする。タブレット横向きは P1、スマートフォンは P2。ステージの解放状態はブラウザ（localStorage）に保存する
- 変更箇所: 要件 NFR-09・NFR-11

### A-24

**決定**: 依頼の期限は通常 60 秒・重要 90 秒、再送は 25 秒（✅ 仮決めのまま）

- いずれもゲーム内時間なので、早送りしても判定は変わらない
- 変更箇所: ステージ定義の `requests`
