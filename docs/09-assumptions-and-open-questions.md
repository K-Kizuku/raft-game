## 2. 各項目の詳細

### A-01

**MVP に Stage 2（2 隻・嵐）と簡易エンジニアパネルを含める**

- 企画書 §14 では「船の複数運行」「嵐・故障イベント」「エンジニアモード」は「余裕があれば」だが、§13 のデモ台本は「嵐で遮断 → 別の船で復旧 → 新しい代表 → エンジニア画面で種明かし」で構成されている。デモを成立させるため、この 3 つの最小限を P0 に前倒しした
- 一方で、Stage 1 だけは「3 島・1 隻・選挙なし」のまま残し、チュートリアルとして使う
- 代替案: Stage 1 に嵐を入れて 1 ステージだけで MVP にする（工数は減るが、1 隻では「別の船で復旧」が見せられない）
- 変更箇所: 要件 §3、進行表 §1、実装計画 M2・M5

### A-02

**インフラは AWS**

- WebSocket を長時間保持し、メモリ上にゲームの状態を持つ Go のサーバーには、常駐するコンテナ（ECS Fargate）が素直に合う。Cloudflare では Go を動かすのに Containers（Durable Objects と組み合わせる）が必要で、ハッカソンの短い期間では情報の少なさがリスクになると判断した
- 代替案と差し替え方: ADR-0011 の代替案 B（Cloudflare Workers + Containers）。アプリのコードは変わらず、`infra/` と CI だけが変わる
- 変更箇所: アーキテクチャ §5、`infra/`、`.github/workflows/deploy.yml`

### A-03

**シミュレーションはサーバーで実行する**

- オーナーの指定（バックエンドは Go）と企画書 §11（WebSocket）に沿った構成。不正の防止・リプレイの記録・将来の協力プレイにも向く
- 代替案: Go を WASM にしてブラウザ内で実行し、サーバーを不要にする。シミュレーションのコアを I/O なしの純粋なライブラリにしてあるので、後からでも移行できる
- 変更箇所: ADR-0009、アーキテクチャ §2

### A-04

**etcd-io/raft v3.7.0 ＋乱数のパッチ**

- 2026-11 時点の最新版。v3.7 は Go 1.26 が必要で、メッセージの型が protobuf-go 製（ポインタ型のフィールド）に変わっている
- `etcd-io/raft` は選挙タイムアウトの乱数に `crypto/rand` を使っており（`raft.go` の `globalRand`）、そのままでは「同じシードで同じ結果」（企画書 §15-6）が実現できない。アルゴリズムには触れず、乱数源だけを注入できるようにする 1 か所のパッチを当てる
- 代替案: パッチを当てずに「記録の再生（再シミュレーションではない）」だけでリプレイを実現する。決定性のテストはできなくなる
- 変更箇所: ADR-0005、`server/third_party/etcd-raft`

### A-05

**舞台の島**

- 隠岐（島後・中ノ島・西ノ島）: 3 島が互いに航路で結ばれ、そのうち 2 島（中ノ島・西ノ島）がとても近いという地理が、「近い島だけで過半数を作る」というトレードオフ（企画書 §6.1）をそのまま表せる。冬の日本海の季節風が嵐のイベントの題材になる
- 伊豆諸島 5 島: 南北に並ぶ配置が、嵐による「北の 2 島 / 南の 3 島」の分断を自然に作れる
- 五島列島 7 島: 人口の大きい島（福江島・中通島）と小さい島の差があり、人口による負荷の偏りを表現できる
- いずれも離島振興法の対象地域として選定（データ D1 に含まれるかは ETL で確認する）
- 代替案: オーナーやチームにゆかりのある地域があれば差し替える（[Q-09](#q-09)）
- 変更箇所: データ仕様 §3.1、ステージ定義、進行表

### A-06

**時間のパラメータ**

- tick 500ms・Heartbeat 1 秒: Leader の定期便が「待っていればまた出る」くらいの頻度にしつつ、港の合流の規則で 1 通にまとまるので画面は煩雑にならない
- 航行 4〜13 秒・停泊 1.5 秒: 3 分のラウンドで 10〜15 回ほど航行でき、1 件の依頼の確定に 20〜40 秒かかる、というテンポを狙った
- 実時間 1 秒 = ゲーム内 1 秒（速度変更は P1）
- 変更箇所: ステージ定義（コードの変更は不要）

### A-07

**選挙タイムアウト**

- Stage 1 は Log Replication に集中させるため、事実上選挙を起こさない（600 秒）
- Stage 2 以降は 20〜40 秒。目安は「Leader と最も近い Follower の往復時間の 2 倍以上」（[DesignDoc §3.2](./03-design-doc.md)）。これより短いと選挙が頻発し、長いと選挙が体験できない
- **プレイテストで最も調整が必要な値**。`simcli` とボットで探索してから人が遊んで決める
- 変更箇所: ステージ定義

### A-08

**PreVote と CheckQuorum を有効にする**

- CheckQuorum: 孤立した Leader が自分から退くので、デモの「嵐で代表がいなくなる」が分かりやすくなる
- PreVote: 孤立していた島が戻ってきたときに Term を無駄に上げて Leader を引きずり下ろすのを防ぐ。これがないと「孤立していた島に手紙を届けると、かえって混乱する」という、プレイヤーにとって理不尽な体験になる
- 代償: 「立候補してもいいかな？」という手紙の種類が増える
- 変更箇所: ADR-0007、ステージ定義の `raft.preVote` / `raft.checkQuorum`（自由実験モードでは切り替えられるようにする）

### A-09

**依頼書による転送**

- `etcd-io/raft` 標準の提案の転送（Follower が `MsgProp` を Leader へ送る）は、Leader が分からないときに黙って捨てられ、再送の仕組みを自分で作る必要がある。どのみちアプリ側で再送と重複の排除が必要なので、転送ごとアプリ側の「依頼書」として見える化した
- 依頼書もフェリーで運ぶので、「住民の依頼を代表の島へ届ける」というゲームらしい手紙になる
- 変更箇所: ADR-0008、DesignDoc §8

### A-10

**依頼の成功は依頼元の島で判定**

- Commit された時点で成功にすると、「Leader と近い島だけで Commit を回し、依頼元の島には結果を届けない」運航が最適になってしまう（企画書 §7 が避けたいこと）
- 依頼元の島に結果が届くまでを仕事にすることで、少数派の島にも船を出す動機が生まれる
- 変更箇所: ADR-0015、ゲームデザイン §4.3・§5

### A-11

**スコアの配点**

- 通常 100 / 重要 300 / 期限後 30 / 期限切れ −50 / 航行 2 秒ごとに −1 / 公平ボーナス 5 × 満足度の最小値（最大 500）
- 公平ボーナスを「平均」ではなく「最小値」にしたのは、1 つの島を見捨てる戦略を明確に不利にするため
- 変更箇所: ゲームデザイン §5、ステージ定義の `scoring`

### A-12

**港キューの規則**

- Heartbeat 系・投票系・記録の返事は、同じ相手への古いものを新しいもので置き換える（意味が同じなので安全）。記録して！は相手ごとに 4 通、港全体で 24 通まで
- 4 は `MaxInflightMsgs` と同じ値（Raft がそれ以上の未応答の `MsgApp` を出さないため、通常は上限に達しない）
- 変更箇所: DesignDoc §6.2、ステージ定義の `transport`

### A-13

**手紙の種類を企画書の 5 種類より増やす**

- 企画書 §5.3 の 5 種類（Heartbeat / App / AppResp / Vote / VoteResp）だけでは、実際の Raft は動かない。Heartbeat の返事（Leader が Follower の生存を知り、遅れている Follower に再送するのに必要）、PreVote とその返事（A-08）、記録の拒否（ログの食い違いの修復）が実際に流れる
- 「本物の Raft のメッセージをそのまま運ぶ」という企画の核を守るため、隠さずに手紙として見せる。ただし色と形で 4 系統（定期便・記録・選挙・依頼書）にまとめ、覚えることを増やさないようにした
- 変更箇所: ゲームデザイン §2

### A-14

**開会式**

- ゲーム開始時は Leader がいない。船で選挙から始めると、最初の数十秒は何をすればよいか分からない
- 開会式で、指定した島に立候補させ（`Campaign()`）、メッセージを即時に配達して選挙を済ませる。当選するかは Raft の投票で決まるので、「ゲーム側が Leader を決めない」（企画書 §10.1）には反しない
- 変更箇所: DesignDoc §5.3

### A-15

**一時停止を許可する**

- 配送「パズル」として、考える時間を持てることを優先した。リアルタイムの緊張感は制限時間と期限で作る
- 代替案: 一時停止を Stage 1 のみ（あるいは回数制限つき）にする（[Q-05](#q-05)）
- 変更箇所: 要件 FR-GAME-04

### A-16

**★2 の条件**

- 「どの島の依頼が成功したか」ではなく「重要な資源が確保されたか」にした。花火の取り合い（2 島が同じ花火を予約）で一方が必ず失敗する設計と、★2 が達成できることを両立させるため
- 変更箇所: ゲームデザイン §4.1・§5.3

### A-17

**デモ専用ステージ**

- 企画書 §13 のデモはプレイ時間が約 1 分 50 秒しかなく、通常のステージの時間感覚では収まらない。時間を圧縮した `demo.yaml` を用意し、嵐は発表者がキーで起こす（話すタイミングに合わせるため）
- 変更箇所: 進行表 §8、ステージ定義

### A-18

**永続化しない**

- ハッカソンでは、ゲームの状態は 1 ラウンド（数分）で終わる。DB を持たないことで、インフラと実装を小さくする
- リプレイの記録はクライアントにダウンロードさせる（P1）。共有リプレイやランキングが必要になったら S3 / DynamoDB を足す
- 変更箇所: ADR-0012

### A-19

**フロントエンドの技術**

- 企画書 §11（React / TypeScript / PixiJS）に沿い、状態管理に zustand、ドラッグ＆ドロップに dnd-kit を足した。PixiJS は React のラッパーを使わず命令的に使い、描画と React の再描画を分ける
- 変更箇所: ADR-0010

### A-20

**WS は JSON、型は Go から生成**

- エンジニアモードでメッセージをそのまま読めること、デバッグのしやすさを優先した。通信量は小さい（1 セッション数 KB/秒）
- 変更箇所: ADR-0014、プロトコル仕様

### A-21

**オープンデータはビルド時に取り込む**

- 実行時に外部のサイトへ依存しない。データの加工の過程を ETL のコードとして残し、再現できるようにする
- 変更箇所: ADR-0013、データ仕様

### A-22

**IaC は Terraform**

- AWS の IaC として情報が多く、Go のチームでも書きやすい。CDK（TypeScript）でもよい
- 変更箇所: ADR-0011、`infra/`

### A-23

**日本語のみ・PC のみ・匿名**

- ハッカソンの審査・デモの環境に合わせた。文言はキーで管理し、後で翻訳できるようにする
- 変更箇所: 要件 NFR-09・NFR-11

### A-24

**依頼の期限と再送**

- 期限: 通常 60 秒・重要 90 秒（1 件の確定に 20〜40 秒かかる想定に対して、少し余裕がある）
- 再送: 25 秒（Leader の交代で提案が消えたときの救済。短すぎると依頼書が増えすぎる）
- 変更箇所: ステージ定義の `requests`

### Q-01

ハッカソンの日程が分かれば、[実装計画](./08-implementation-plan.md) を日単位の計画に落とします。期間が 2 日以下なら、Stage 2 の嵐とエンジニアパネルに絞り、Stage 1 のチュートリアルを簡略化する案を推奨します。

### Q-02

[データ仕様 §2](./07-data-spec.md) を参照。島ごとの人口・面積がそろっていれば、残りは ETL の入力の形を合わせるだけです。

### Q-03

AWS が使えない場合は ADR-0011 の代替案 B（Cloudflare）に差し替えます。

### Q-04

会場の回線が不安定な場合、ノート PC でサーバーを起動するデモが最も確実です。

### Q-05

一時停止を禁止すると、緊張感は増しますが、非エンジニアには難しくなります。

### Q-06
