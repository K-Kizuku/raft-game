# ADR-0017: 操作の記録を Durable Object に保存して復元・リプレイに使い、リプレイの共有に R2 を使う

- 状態: Accepted
- 日付: 2026-11-06
- 決めた人: プロダクトオーナー（A-18 で案 c を選択）、Claude（具体化）
- 関連: FR-LOG、FR-GAME-07・09、ADR-0005、ADR-0016、[DesignDoc §10・§12](../03-design-doc.md)
- 置き換える ADR: [ADR-0012](./0012-no-persistence-in-mvp.md)（MVP では永続化しない）

## 背景

ADR-0012 では「すべてメモリのみ」を仮決めしていた。その後、インフラが Cloudflare に決まり（ADR-0016）、1 ゲーム＝1 Durable Object＝1 コンテナになった。これで状況が 2 つ変わった。

- Durable Object には、標準で SQLite の保存領域がある
- Cloudflare のコンテナは、長く通信がないときや、デプロイ・障害のときに止まることがある。ゲームの状態をコンテナのメモリにしか持たないと、そのときにゲームが失われる

一方、このゲームは決定的（ADR-0005）なので、**「ステージ・シード・時刻付きの操作列」さえあれば、ゲームの状態をいつでも再計算できる**。操作の記録は 1 ゲームで数 KB と小さい。

## 検討した選択肢

### 案 a: 何も保存しない（ADR-0012）

- 長所: 最も小さい
- 短所: コンテナが止まるとゲームが失われる。リプレイはブラウザに残したものしかない

### 案 b: 操作の記録を Durable Object に保存する

- 長所: 作業が小さい。コンテナが止まっても復元できる。リプレイをサーバーから取り出せる
- 短所: Durable Object とコンテナの間の取り決めが増える

### 案 c: 案 b ＋ リプレイを R2 に保存して共有する

- 長所: リプレイの共有やランキングの土台になる
- 短所: MVP には必須ではない

## 決定

案 c。ただし時期を分ける。

| 対象 | 保存先 | 時期 |
|---|---|---|
| セッションの情報（ステージ・シード・トークンのハッシュ・状態・作成時刻） | Durable Object の SQLite | P0 |
| 操作の記録（`t` とコマンドの組の列） | Durable Object の SQLite | P0 |
| ラウンドの結果（スコア・統計） | Durable Object の SQLite | P0 |
| リプレイの共有（入力ログの JSON） | R2（`raft-game-replays`）。推測できない ID の URL で共有する | P1 |
| Raft のログ・HardState | コンテナのメモリ（`raft.MemoryStorage`）のまま。ログのコンパクションもしない | — |

### 記録の流れ

1. Durable Object は、ブラウザとコンテナの間の WebSocket を中継する
2. コンテナは、コマンドを適用したら `ack` に**適用したゲーム内時刻 `t`** を入れて返す
3. Durable Object は、クライアントから来たコマンドと、それに対する成功した `ack` の `t` を組にして、SQLite に追記する
4. 一時停止・速度の変更のコマンドも記録する（リプレイでの見た目の再現用。シミュレーションの結果には影響しない）

### 復元の流れ

1. コンテナが応答しなくなったら、Durable Object は新しいコンテナを起動する
2. Durable Object は、内部の電文 `internal.restore` で、ステージ・シード・操作の記録をコンテナに渡す
3. コンテナは、記録の最後の時刻まで一気に再計算し、一時停止の状態で待つ
4. ブラウザには `snapshot` が届き、プレイヤーが再開を押すと続きから遊べる

### 追記（2026-11-07、T-302）

`stageHash`・`build` はコンテナが `snapshot` の `session`（`session.stageHash`・`session.build`）で知らせ、Durable Object が保存して入力ログに入れる。`internal.restore` の `until` で、最後に中継した時刻（`clock.t`）まで戻せる（省略すれば最後のコマンドの `t`）。入力ログの `build` がコンテナと違っても復元を試み、食い違えば `restore_failed` を返す。最後の `TraceHash` の照合は P1。詳しくは[プロトコル §9](../06-protocol.md#9-内部の電文durable-object--コンテナ)。

## 結果

- 良いこと: コンテナが止まっても、遊んでいる途中のゲームが失われない（FR-GAME-09）。リプレイをサーバーから取り出せる（FR-LOG-03）。R2 の共有で、将来のランキングや「うまくいった回」のデモ再生にもつながる
- 悪いこと: Durable Object に、記録と復元の処理（TypeScript）が増える。決定性が崩れると復元も崩れるので、決定性のテスト（V-6）の重要度が上がる

## 差し替えるときの影響範囲

`web/worker/`（Durable Object）、`server/internal/server`（`ack` の `t`、`internal.restore`）、プロトコル仕様 §4・§9、DesignDoc §10・§12。

## 見直すきっかけ

- 協力プレイ（複数の WS 接続）を作るとき（操作の記録の順序の決め方を見直す）
- ランキングを作るとき（R2 に加えて、検索のための保存先が必要になる）
