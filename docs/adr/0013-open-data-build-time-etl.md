# ADR-0013: オープンデータはビルド時の ETL で取り込む

- 状態: Accepted（2026-11-06 にプロダクトオーナーが承認）
- 日付: 2026-11-01
- 決めた人: Claude
- 関連: C-06、FR-DATA、[データ仕様](../07-data-spec.md)

## 背景

国土交通省の離島関連データ（地域一覧・振興計画書・事業計画書）を使う。当初は形式を CSV・Excel・PDF などと想定し、計画書は文章なので機械的には取り込めないと考えていた。企画書は「行政計画の文章から抽出した情報と、ゲーム上の創作設定を明確に区別する」ことを求めている。

## 検討した選択肢

### 案 A: ビルド時に Go の ETL で JSON を生成し、生成物をコミットする。計画書の文章は人手で要約して出典付きの YAML にする

- 長所: 実行時に外部のサイトに依存しない。加工の過程がコードとして残り、再現できる。生成物の差分がレビューできる
- 短所: データが更新されたら ETL を再実行してコミットする必要がある

### 案 B: 実行時にデータの公開元から取得する

- 長所: 常に最新
- 短所: 公開元が API を提供しているとは限らない。デモの日に公開元が落ちていると動かない。決定性が崩れる

### 案 C: 必要な値を手でステージ定義に書く

- 長所: 最も早い
- 短所: 出典と加工の過程が残らない。「オープンデータを活用した」根拠が弱くなる

## 決定

案 A。すべての値に出典区分（`fact` / `derived` / `creative`）を付ける。数値の加工（人口 → 依頼の重み）は、ステージの読み込み時に行う。

### 2026-11-06 の追記（提供データを確認した結果）

- 提供データは「国土交通省 Project LINKS アイディアソン公開データ（2026年度）離島に関するデータ」で、すべて **CSV（UTF-8、BOM 付き）**とデータ定義書（xlsx）だった。利用規約は政府標準利用規約（第 2.0 版）
- 計画書も CSV なので、文章（海上交通・気象・観光・防災など）は **ETL で機械的に取り込む**。人手の作業は、所要時間・欠航率などの値の抜き出し（出典の地域・項目・引用を記録）と、使う文章の選定だけになった
- 元の CSV も `data/raw/` にコミットする（利用規約が出典の記載を条件に再配布を認めているため）
- 人口の一覧には 8 つの基準日の値が並ぶので、最新（令和 8 年 4 月 1 日）を使う。複数の自治体にまたがる島は合計する（`derived`）
- 詳細は [データ仕様](../07-data-spec.md)

## 結果

- 良いこと: 「この数字はどこから来たのか」を画面とデータの両方で示せる
- 悪いこと: 計画書の要約は人手の作業になる（ステージに出す島の分だけに絞る）

## 差し替えるときの影響範囲

`server/cmd/islandsdata`、`data/`。
