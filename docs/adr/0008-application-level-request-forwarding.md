# ADR-0008: 提案の転送はアプリ層の「依頼書」で行う

- 状態: Proposed（仮決め）
- 日付: 2026-11-01
- 決めた人: Claude
- 関連: 企画書 §5.3（アプリケーション用の手紙）・§15（一意な ID と再送）、FR-MAIL-06、FR-REQ-06・09、[DesignDoc §8](../03-design-doc.md)

## 背景

住民の依頼は、どの島でも発生する。Raft では、ログへの提案（Propose）は Leader でしか受け付けられない。Follower で発生した依頼を Leader へ届ける方法を決める必要がある。

## 検討した選択肢

### 案 A: `etcd-io/raft` 標準の転送（Follower の `Propose` が `MsgProp` として Leader へ送られる）

- 長所: Raft のメッセージとして自然に流れる
- 短所: Follower が Leader を知らないとき、提案は `ErrProposalDropped` で捨てられる。転送された先がすでに Leader でなかった場合も捨てられる。いずれにせよアプリ側で再送の仕組みが必要。どの依頼がどこで捨てられたかを追いにくい

### 案 B: `DisableProposalForwarding = true` にし、アプリ層（島の「役場」）が「依頼書」という手紙を Leader へ送る

- 長所: 依頼書を港・船で運ぶので、「住民の依頼を代表に届ける」というゲームらしい手紙になる（企画書 §5.3 の「アプリケーション用の手紙」）。再送・転送・重複の排除をアプリ層で一貫して扱える。依頼の状態（送付待ち・輸送中・審議中）を正確に追える
- 短所: Raft の外の仕組みが 1 つ増える

## 決定

案 B。役場の振る舞いは次のとおり（詳細は DesignDoc §8）。

- 自分が Leader なら `Propose`、Leader を知っていれば依頼書を書いて港へ、知らなければ待つ
- 依頼書を受け取った島が Leader でなければ、自分が知っている Leader へ転送する
- 依頼元の島は、25 秒たっても自分の台帳に適用されなければ再送する
- 依頼には一意な ID を付け、台帳は同じ ID の 2 回目以降の適用を `duplicate` として無視する（企画書 §15）

## 結果

- 良いこと: 依頼の流れがすべて手紙として見える。Raft の提案の転送で起きる「黙って捨てられる」問題を、プレイヤーにも分かる形（再送）で扱える
- 悪いこと: Leader が提案した後、Commit 前に交代するとエントリが消えることがあり、そのときは再送を待つことになる（これは Raft の実際の振る舞いであり、エンジニアモードで観察できる）

## 差し替えるときの影響範囲

`server/internal/game`（役場）、`server/internal/cluster`（`DisableProposalForwarding`）、ゲームデザイン §2・§4、プロトコル仕様の `request` 手紙。

## 見直すきっかけ

- 依頼書と Raft の手紙が混ざって分かりにくい、というプレイテストの結果が出たとき
