# ADR-0018: コストガード — 意図しない課金の増加を、アプリ側の上限で防ぐ

- 状態: Accepted
- 日付: 2026-11-06
- 決めた人: プロダクトオーナー（6 つの仕組みの導入、月 30 USD の上限、いつでも無効にできること、署名の確認は無効にしない運用）、Claude（調査と設計）
- 関連: NFR-07・15、FR-COST、ADR-0016、ADR-0017、[判断の記録 R-01・R-05・R-06](../09-assumptions-and-open-questions.md)

## 背景

- 近年、AI などの bot のクローリングで、PoC のアプリにも大量のアクセスが来て、課金額が膨らむ事例が起きている。特に Durable Objects で費用が急増した事例がある
- オーナーは、**Cloudflare 全体で、一定の金額を超えた課金が発生しない仕組み**を入れたい
- 一方で、**開発中やデモの最中に急に動かなくなると困る**ので、仕組みは最初から入れつつ、**いつでも無効にできる**必要がある

### 調べた事実（公式ドキュメント、2026-11 時点）

| 項目 | 内容 |
|---|---|
| 上限で止める仕組み（ハードキャップ） | **公式にはない**。第三者の記事に「試作中、2026 年第 4 四半期に提供予定」とあるが、公式には確認できない |
| 予算アラート | 「Billing > Billable Usage」または「Notifications」で設定する。**メールで知らせるだけで、利用は止まらない**。集計は 1 日 1 回で、前日分が翌日に届く。従量課金の分だけが対象（月 5 USD の基本料金は含まない）。2026-06 から、既定で 10 USD のアラートが作られる |
| 静的ファイル | リクエストは**無料・無制限** |
| Worker | 月 1,000 万リクエストまで含む（超過は 100 万あたり 0.30 USD）。CPU 時間は月 3,000 万 ms まで含む（超過は 100 万 ms あたり 0.02 USD）。公式は「意図しない高額請求や、費用を狙った攻撃を防ぐ」ために、1 回あたりの CPU 時間の上限（`limits.cpuMs`）の設定を勧めている |
| Durable Object | リクエストは月 100 万まで含む（超過は 100 万あたり 0.15 USD。WebSocket の受信は 20 件で 1 件、アラームの呼び出しも 1 件）。動いている時間は月 40 万 GB 秒まで含む（超過は 100 万 GB 秒あたり 12.50 USD。割り当て 128 MB で計算）。受け付けた WebSocket がつながっている間は課金される。休止できる API（Hibernation）もあるが、Durable Object から外へ張った WebSocket は休止しない |
| Containers | ADR-0016 の料金の行のとおり |
| Workers Logs | 月 2,000 万件まで含む（超過は 100 万件あたり 0.60 USD） |

費用が急増した事例の多くは、「Durable Object の接続やアラームが止まらずに動き続けた」か、「外から好きな ID で Durable Object を作れた」のどちらかが原因だった。

## 検討した選択肢

### 案 A: Cloudflare の予算アラートだけに頼る

- 長所: 作業がない
- 短所: 止まらない。届くのは翌日

### 案 B: アプリ側で「お金がかかる操作」の総量に上限をかけ、加えて入り口で bot を止める（コストガード）

- 長所: 設計の上で「最悪でもこの金額まで」を決められる。Cloudflare の機能が増えるのを待たなくてよい
- 短所: 作業が増える。見積もりは料金表に基づく推定で、実際の請求とは一致しない

### 案 C: 同時に動くゲームの数に上限をかける

- 長所: 単純
- 短所: 合計の費用は抑えられない。オーナーの判断で不採用（R-01）

## 決定

案 B。次の 6 つの仕組みを、**最初からすべて有効にして**導入する。

| # | 仕組み | 内容 | 無効にできるか |
|---|---|---|---|
| G1 | **費用の上限（会計係）** | 全体で 1 つだけの Durable Object `CostGuard` が、ゲームごとの見込みの費用を合計する。上限は **1 か月 30 USD・1 日 1 USD**。上限に達したら、新しいゲームの受付を止める（「本日の受付は終了しました」）。一般公開とデモ用の Worker で同じ `CostGuard` を共有する | できる（管理用 API） |
| G2 | **1 ゲームの時間の上限** | 1 ゲームは最長 30 分で打ち切る。ラウンドが終わったらすぐにコンテナを止める（`destroy()`）。アラームは、1 つのゲームで設定できる回数に上限を設け（例：20 回）、繰り返しが止まらなくなることを防ぐ | 時間の上限は変えられる（管理用 API）。アラームの回数の上限は常に有効 |
| G3 | **署名の確認** | セッション ID に署名（HMAC）を付ける。Worker が署名を確かめてから Durable Object を呼ぶので、でたらめな ID では Durable Object もコンテナも作られない | **できない**（下の注意を参照） |
| G4 | **入り口での bot の遮断** | ゲームを始めるとき（`POST /api/sessions`）に Cloudflare Turnstile を通す。Worker の中で IP ごとのレート制限（1 分に 10 回）。`kizuku-hackathon.work` のゾーンでは、2 つのホスト名に限定した WAF のレート制限と、AI クローラーの遮断を設定する | Turnstile と Worker のレート制限はできる（管理用 API）。ゾーンの設定は `cf` で外す |
| G5 | **CPU 時間の上限** | `limits.cpuMs` で CPU 時間に上限をかける。T-007 の本番向け暫定候補は 500 ms。WS の電文と fetch ログの集計の範囲は ADR-0016 を参照 | できる（設定を変えて再デプロイ。数分かかる） |
| G6 | **早く気づいて、すぐ止める** | Cloudflare の予算アラートを 5 USD に設定する。緊急時に、新しいゲームの受付を一括で止めるスイッチ（管理用 API）を用意する | —（気づくための仕組み） |

> **注意（G3：署名の確認は無効にしない）**
> 署名の確認を無効にすると、外から好きな ID で Durable Object とコンテナを作れるようになり、Durable Object で費用が急増する典型的な原因になる。開発中もデモの最中も、**この仕組みは無効にしない運用**とする。そのため、管理用 API の切り替えの対象からも外している。どうしても外す必要がある場合は、この ADR を改訂してからにする。

### 見込みの費用の計算

ゲームを始めるときに**最悪の費用を予約**し、終わったら**実際に動いた時間で精算**する。

| マシンの大きさ | 最悪の費用（30 分） | 内訳 |
|---|---|---|
| `lite`（一般公開） | 約 0.0065 USD | コンテナ 約 0.0036 USD（メモリ 0.25 GiB・CPU 1/16 vCPU・ディスク 2 GB）＋ Durable Object 約 0.0028 USD（128 MB） |
| `standard-1`（デモ） | 約 0.040 USD | コンテナ 約 0.037 USD（メモリ 4 GiB・CPU 1/2 vCPU・ディスク 8 GB）＋ Durable Object 約 0.0028 USD |

- 単価は 2026-11 時点の公式の料金表の値。有料プランに含まれる分は差し引かない（安全側に見積もる）
- 目安として、一般公開だけなら 1 日 150 ゲーム程度で 1 日の上限（1 USD）に達する。デモ用で 1 回遊ぶと、一般公開の約 6 ゲーム分を使う
- 単価は `GUARDS` の設定に持たせ、料金が変わったら設定を直す

### T-007 後の値と見積もりの範囲

- 一般公開 lite / デモ standard-1 を維持するため、上のコンテナと DO の 30 分の予約単価は変更しない。負荷模型の結果と判断は [ADR-0016](./0016-infrastructure-cloudflare-with-cf-cli.md) を参照。
- CPU 上限の暫定候補は 50 ms から 500 ms に引き上げる。1 回あたりに許す CPU 消費量は 10 倍になるが、実際の CPU 使用量や請求が 10 倍になったという意味ではない。通常の Worker fetch では p99 / 最大 3 ms を観測した。
- この予約表はコンテナと DO の時間課金の見積もり。入口 Worker のリクエスト・CPU や Logs は別に監視する。500 ms の設定も G1 の受付停止も、アカウント全体の請求のハードキャップにはならない。
- ラウンド終了の destroy と回数上限付きアラームを使う。T-007 では inactivity の設定が成功しても 60 秒後に止まらなかったため、inactivity 単独を費用停止の保証にしない。

### 無効にする方法（いつでも）

- 各仕組みの既定値は、`cloudflare.config.ts` の `GUARDS`（モードごと）に書き、**最初はすべて有効**にする
- 管理用 API で、再デプロイなしに数秒で切り替えられる

| メソッド | パス | 内容 |
|---|---|---|
| GET | `/api/admin/guards` | 現在の設定と、今日・今月の見込みの費用 |
| PATCH | `/api/admin/guards` | 個別の仕組みの有効・無効、上限の値、受付の一括停止を変える。値は `CostGuard` に保存され、設定ファイルの既定値より優先される |

- 管理用 API は `Authorization: Bearer <ADMIN_TOKEN>` を必須にする。`ADMIN_TOKEN` は `--secrets-file` で渡し、リポジトリには入れない
- 切り替えた記録（いつ・何を）は `CostGuard` の SQLite に残す
- 例：デモの最中に 1 日の上限に達しそうになったら、その場で G1 を無効にする

## 結果

- 良いこと: Cloudflare に上限で止める機能がなくても、このアプリの費用の最大値を設計で決められる。開発中やデモでは、必要に応じてその場で外せる
- 悪いこと・受け入れるリスク:
  - 見込みの費用は推定で、実際の請求とずれる（安全側に見積もる）
  - Worker の呼び出しそのもの（入り口）の費用は、G1 では止められない。G4（WAF）と G5 で抑える
  - `CostGuard` は全体で 1 つなので、ゲームの開始が集中すると待ちが発生しうる（ゲームの開始時と終了時にしか呼ばないので、ハッカソンの規模では問題にならない想定）
  - 管理用の合言葉が漏れると、仕組みを外される。合言葉は定期的に変える

## 差し替えるときの影響範囲

`web/worker/cost-guard.ts`（`CostGuard`）、`web/worker/index.ts`（署名・Turnstile・レート制限）、`web/cloudflare.config.ts`（`GUARDS`・`limits`）、`scripts/cloudflare/`（ゾーンの設定）、プロトコル仕様 §2、要件 FR-COST。

## 見直すきっかけ

- Cloudflare が公式に上限で止める機能を提供したとき（G1 をそれに置き換えるか検討する）
- 料金が変わったとき（`GUARDS` の単価を直す）
- 実際の請求と見込みが大きくずれたとき
