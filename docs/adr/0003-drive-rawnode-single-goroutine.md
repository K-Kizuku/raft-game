# ADR-0003: `RawNode` を単一 goroutine で駆動する

- 状態: Proposed（仮決め）
- 日付: 2026-11-01
- 決めた人: Claude
- 関連: NFR-04、V-5、V-6、[DesignDoc §5](../03-design-doc.md)

## 背景

`etcd-io/raft` には 2 つの API がある。

- `raft.Node`: 内部に goroutine を持ち、チャネル（`Ready()`・`Tick()` など）でやり取りする
- `raft.RawNode`: goroutine を持たず、呼び出し側が同期的に `Tick()`・`Step()`・`Ready()`・`Advance()` を呼ぶ

ゲームでは「同じ入力から同じ結果」（決定性）が必要で、テスト・リプレイ・デモの再現の土台になる。

## 検討した選択肢

### 案 A: `RawNode` を、1 セッション 1 goroutine の中で、全ノード分まとめて同期的に駆動する

- 長所: goroutine のスケジューリングによる揺らぎがなく、決定的。ロックが要らない。Ready の処理の順序を 1 つの関数で管理できる
- 短所: ノードが並列に動かない（ゲームの規模では問題にならない）

### 案 B: `raft.Node` をノードごとの goroutine で動かす

- 長所: 実際のサーバーの構成に近い
- 短所: チャネルの受信順が実行ごとに変わり、決定性が失われる。テストの再現が難しい

## 決定

案 A。`RawNode` だけを使い、`raft.Node` は使わない。

## 結果

- 良いこと: シミュレーション全体が決定的になる。セッションの中にロックがない
- 悪いこと: 将来「各ノードを独立したコンテナで動かす」（企画書 §11）方式に拡張するときは、ノードごとの駆動ループを別に書く必要がある（`cluster.Node` のインターフェースはそのまま使える）

## 差し替えるときの影響範囲

`server/internal/cluster`、`server/internal/sim`、DesignDoc §4・§5。

## 見直すきっかけ

ノードを複数のプロセス・コンテナに分ける構成を作るとき。
