# ADR-0002: Raft の実装に etcd-io/raft を使う

- 状態: Accepted（2026-11-06 にプロダクトオーナーが承認）
- 日付: 2026-11-01
- 決めた人: Claude（企画書 §10.1 の指定を確認）
- 関連: C-04、C-05、[DesignDoc §5](../03-design-doc.md)、ADR-0003、ADR-0005

## 背景

企画書は「Raft を模倣した独自の状態遷移ではなく、実際の Raft 実装を使う」「Go 製の `etcd-io/raft`」と指定している。ゲームでは、ネットワーク（輸送）をプレイヤーの操作で置き換える必要があり、ライブラリがその置き換えを許すかが重要。

## 検討した選択肢

### 案 A: `go.etcd.io/raft/v3`（etcd-io/raft）

- 長所: 企画書の指定どおり。etcd・CockroachDB などの本番で使われている実装。**ネットワーク・ストレージ・時計を持たない**設計（利用者が `Tick()`・`Step()`・`Ready()` で駆動する）なので、輸送をフェリーに置き換えるのにそのまま向いている
- 短所: 利用者が書くべきこと（Ready の処理の順序、ストレージ）が多い。v3.7 で API が変わり（protobuf-go への移行）、Web 上のサンプルがそのまま使えない

### 案 B: `hashicorp/raft`

- 長所: Transport のインターフェースがあり、差し替えの口が明確
- 短所: 内部で goroutine と実時間のタイマーを使うので、仮想時間での決定的なシミュレーション（ADR-0004）が難しい。企画書の指定と違う

### 案 C: 自作

- 長所: ゲームに合わせて自由に作れる
- 短所: 企画書の核である「本物の Raft」でなくなる。正しさの検証に時間がかかる

## 決定

案 A。版は **v3.7.0**（2026-11 時点の最新、Go 1.26 が必要）に固定する。

## 結果

- 良いこと: 「本物の Raft が動いている」と胸を張って言える。輸送の差し替えにライブラリの改変が要らない
- 悪いこと: v3.7 の API に慣れるまで時間がかかる（実装計画の T-101 で最初に最小の例を作って吸収する）。乱数源の問題は ADR-0005 で対処する

## 差し替えるときの影響範囲

`server/internal/cluster` 全体、`server/third_party/etcd-raft`、DesignDoc §5、プロトコル仕様の `raft` フィールド。

## 見直すきっかけ

- v3.7 の API で実装が詰まり、v3.6（gogo-protobuf 製、サンプルが多い）に下げたほうが早いと判断したとき（その場合も ADR-0005 のパッチは同様に当てられる）
- Raft 以外のアルゴリズム（CRDT・Gossip、企画書 §17）のモードを追加するとき（この ADR はそのまま、別の ADR を追加）
