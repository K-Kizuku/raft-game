# ADR-0009: シミュレーションはサーバーで実行し、WebSocket で配信する

- 状態: Proposed（仮決め）
- 日付: 2026-11-01
- 決めた人: Claude（オーナーの指定「バックエンドは Go」と企画書 §11 に沿って）
- 関連: C-01・C-02、NFR-02・03、[アーキテクチャ §2](../02-architecture.md)、[プロトコル仕様](../06-protocol.md)

## 背景

Raft クラスタとゲームのルールを、どこで動かすかを決める必要がある。オーナーの指定は「フロントエンドは Web、バックエンドは Go」、企画書は「WebSocket でゲームイベントをリアルタイムに配信」。

## 検討した選択肢

### 案 A: サーバー（Go）でシミュレーションを実行し、状態の変化をイベントとして WebSocket で配信する（サーバー権威型）

- 長所: 指定どおり。ゲームの状態はサーバーにしかないので、不正やクライアントの改ざんの影響を受けない。入力ログ・トレースをサーバーで確実に記録できる。複数人の協力プレイ（P2）に拡張しやすい
- 短所: サーバーの運用が必要。通信の遅延が操作の反応に乗る（ゲームの性質上、100ms 程度の遅延は問題にならない）。セッションの状態がサーバーのメモリにあるので、再デプロイで切れる

### 案 B: Go のシミュレーションを WASM にしてブラウザで実行する（サーバーは静的配信だけ）

- 長所: サーバーの運用が要らない（Cloudflare Pages / S3 だけで済む）。遅延ゼロ。オフラインでも遊べる
- 短所: 「バックエンドは Go」という指定の意図（サーバーを Go で書く）から外れる可能性がある。WASM のサイズ（数 MB）と起動時間。記録の収集がクライアント任せになる

### 案 C: サーバーで実行し、状態を毎フレームまるごと送る

- 長所: クライアントの実装が単純
- 短所: 通信量が多い。イベント（「手紙が配達された」）としての意味が失われ、演出が作りにくい

## 決定

案 A。サーバーからは「スナップショット（全体の状態）」と「ドメインイベントの差分」を送り、船の位置などの連続的な値はクライアントが補間する。

ただし、案 B への道を残すため、**シミュレーションのコア（`internal/sim` 以下）は I/O を持たない純粋なライブラリ**にする。WASM 化するときは、`sim.Engine` を JS から呼ぶ薄い層を書けばよい。

## 結果

- 良いこと: 指定に沿っている。ゲームの状態とルールが 1 か所にある
- 悪いこと: セッションがサーバーのメモリにあるので、デモの前はデプロイを凍結する運用が必要

## 差し替えるときの影響範囲

`server/internal/server`、`web/src/net`、`infra/`、プロトコル仕様。シミュレーションのコア（`internal/sim` 以下）とクライアントの描画は変わらない。

## 見直すきっかけ

- サーバーの運用（費用・デプロイの凍結）が負担になったとき → 案 B
- 会場の回線が不安定で、オフラインで動くデモが必要になったとき → まず `make demo-local`、次に案 B
