# ADR-0006: Ferry Transport を Raft の外側に置き、港キューに上限と合流の規則を設ける

- 状態: Proposed（仮決め）
- 日付: 2026-11-01
- 決めた人: Claude（企画書 §10.2・§15-7 を具体化）
- 関連: FR-MAIL-01・03、V-4、V-7、[DesignDoc §6](../03-design-doc.md)

## 背景

企画書の核は「Raft 自体は変更せず、ネットワークの条件だけをプレイヤーの操作で変える」こと。`etcd-io/raft` は送信を利用者に任せる（`Ready.Messages` を利用者が届ける）ので、届け方をフェリーにすればよい。ただし、Leader は 1 秒ごとに Heartbeat を出し、返事がなければ `MsgApp` を送り直すので、何もしないと港の手紙が増え続ける（企画書 §15-7）。

## 検討した選択肢

### 案 A: Raft の外側に港キュー・フェリーの層を置き、港で「同じ意味の古い手紙を新しい手紙で置き換える（合流）」「種類ごとの上限を超えたら古いものから捨てる」

- 長所: Raft に手を入れない。捨てることはネットワークでの欠落と同じなので、Raft の安全性は保たれる。画面の手紙の数も抑えられる
- 短所: どの手紙が合流・破棄されたかをプレイヤーに分かりやすく伝える工夫が必要

### 案 B: 港キューに上限を設けず、すべて残す

- 長所: 実装が単純。何も捨てないので説明が要らない
- 短所: 手紙が増え続け、画面が手紙で埋まる。メモリも増え続ける

### 案 C: Leader の Heartbeat の頻度を極端に下げて手紙を減らす

- 長所: 手紙の数自体が減る
- 短所: 選挙タイムアウトとの関係（Heartbeat の間隔 < 選挙タイムアウト）が崩れやすい。合流をしないと根本的には解決しない

## 決定

案 A。規則は [DesignDoc §6.2](../03-design-doc.md) の R1〜R6（Heartbeat 系・投票系・記録の返事の合流、相手ごとの `MsgApp` 4 通、港全体 24 通、依頼書は同じ依頼 ID で合流）。手紙の内容（Raft メッセージ）は一切書き換えない。

中継港（積み替え）では、手紙を預かるだけで Raft では処理しない（企画書 §10.2）。

## 結果

- 良いこと: 港・船・中継倉庫の手紙の数に上限があることを保証できる（V-7）。Raft の安全性に依存した設計になる（企画書 §15 の「遅延・重複・破棄は起こり得るものとして扱う」）
- 悪いこと: 合流は「プレイヤーが運ばなかった手紙が消える」ように見えることがある。表示の工夫（「新しい手紙に差し替わりました」）が必要

## 差し替えるときの影響範囲

`server/internal/ferry`、ステージ定義の `transport`、ゲームデザイン §2.3。

## 見直すきっかけ

- プレイテストで「手紙が勝手に消える」ことが不満として多く挙がったとき（合流を見える化する、または上限を上げる）
- 規則の値（4 通・24 通）はステージ定義で調整する（この ADR の差し替えは不要）
