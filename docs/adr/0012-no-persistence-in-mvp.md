# ADR-0012: MVP では永続化しない

- 状態: Proposed（仮決め）
- 日付: 2026-11-01
- 決めた人: Claude
- 関連: FR-LOG、[DesignDoc §5.2・§10](../03-design-doc.md)、ADR-0011

## 背景

永続化の対象になりうるものは 3 つある。

1. Raft のストレージ（ログ・HardState）
2. ゲームのセッション（遊んでいる途中の状態）
3. 記録（入力ログ・トレース・スコア）

## 検討した選択肢

### 案 A: すべてメモリのみ。記録はクライアントにダウンロードさせる（P1）

- 長所: DB が要らず、インフラと実装が小さい。Raft のストレージは `raft.MemoryStorage` をそのまま使える
- 短所: サーバーが再起動すると、遊んでいる途中のセッションは失われる。ランキングや共有リプレイは作れない

### 案 B: 記録を S3、スコアを DynamoDB に保存する

- 長所: 共有リプレイ・ランキングが作れる
- 短所: MVP には不要な機能のためにインフラが増える

### 案 C: Raft のストレージを実際にディスクに書く

- 長所: 「永続化」の順序（企画書 §15-5）を本物のディスクで確かめられる
- 短所: ゲームのラウンドは数分で終わり、ノードの再起動（クラッシュ）もゲームの要素にしていないので、意味がない。決定性も損なう

## 決定

案 A。Raft のストレージは `raft.MemoryStorage`。Ready の処理の順序（永続化 → 送信 → 適用）はメモリ上のストレージに対しても守り、テストで確認する（V-5）。

ログのコンパクション（スナップショット）も行わない。1 ラウンドのログは数百エントリにしかならないため。

## 結果

- 良いこと: 実装・インフラ・費用が小さい
- 悪いこと: 再デプロイでセッションが切れる。`MsgSnap` が発生しない（発生したらバグとして検出する）

## 差し替えるときの影響範囲

案 B に進む場合: `server/internal/server`（記録の保存）、`infra/`（S3・DynamoDB）、プロトコル仕様（リプレイの共有）。シミュレーションのコアは変わらない。

## 見直すきっかけ

- ランキング・共有リプレイ・協力プレイを作るとき
- 「島（ノード）の再起動」をゲームのイベントにするとき（そのときは `MemoryStorage` の内容を保持したままノードを作り直す）
