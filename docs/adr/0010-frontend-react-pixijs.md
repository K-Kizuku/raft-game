# ADR-0010: フロントエンドは React + PixiJS v8

- 状態: Proposed（仮決め）
- 日付: 2026-11-01
- 決めた人: Claude（企画書 §11 の「React / TypeScript」「PixiJS など」を具体化）
- 関連: NFR-01・09・10、[DesignDoc §13](../03-design-doc.md)

## 背景

画面は「マップ（島・航路・船・手紙のアニメーション）」と「パネル類（HUD・フェリー操作・島の詳細・エンジニアパネル・リザルト）」に分かれる。前者は描画の性能、後者は UI の作りやすさが重要。

## 検討した選択肢

### 案 A: React（パネル類）＋ PixiJS v8（マップ、React の外で命令的に使う）＋ zustand ＋ dnd-kit ＋ Vite

- 長所: 企画書の指定どおり。パネル類（文字・表・ドラッグ＆ドロップ・アクセシビリティ）は DOM のほうが作りやすい。PixiJS は WebGL / WebGPU で、手紙 200 通程度は余裕で描ける。zustand はストアを React の外（PixiJS の描画ループ）からも読める
- 短所: 2 つの描画系をまたぐ（マップ上の手紙をパネルへドラッグする、など）操作の実装に工夫が要る → 積み込みのドラッグ＆ドロップは DOM のパネル内（港の手紙 → 積み荷スロット）で完結させる

### 案 B: Phaser（ゲームエンジン）で全部を作る

- 長所: ゲームのための機能（シーン・トゥイーン・入力）がそろっている
- 短所: 表やフォームの多いパネル類（エンジニアパネル）が作りにくい。React と組み合わせるなら、案 A と同じ問題が出る

### 案 C: React ＋ SVG / Canvas 2D で全部を作る

- 長所: 依存が少ない。SVG なら DOM と同じ扱いで操作できる
- 短所: 要素が増えると性能が落ちる。アニメーションの作り込みが大変

### 案 D: `@pixi/react` で PixiJS を React のコンポーネントとして使う

- 長所: React の書き方でマップも書ける
- 短所: 毎フレームの更新が React の再描画を経由しやすい。ライブラリの版の追従のリスク

## 決定

案 A。

| 用途 | ライブラリ |
|---|---|
| UI | React 19 + TypeScript |
| マップの描画 | PixiJS v8 |
| 状態 | zustand |
| ドラッグ＆ドロップ | dnd-kit |
| ビルド | Vite |
| テスト | Vitest、Playwright |
| パッケージ管理 | pnpm |

## 結果

- 良いこと: 企画書の指定に沿う。マップとパネルの責務が分かれ、並行して作れる
- 悪いこと: マップ上の要素（島をクリック → パネルに表示）と DOM の連携は、ストアを介して行う必要がある

## 差し替えるときの影響範囲

`web/src/game`（マップ）、`web/src/ui`。WS クライアントとストア（`web/src/net`・`web/src/state`）は変わらない。

## 見直すきっかけ

- 素材（イラスト・アニメーション）が増え、ゲームエンジンの機能が必要になったとき
