# ADR-0015: 依頼の成功は依頼元の島で適用された時点で判定する

- 状態: Proposed（仮決め）
- 日付: 2026-11-01
- 決めた人: Claude
- 関連: 企画書 §5.4・§7、FR-REQ-08、FR-SCORE-02、[ゲームデザイン §4.3・§5](../04-game-design.md)

## 背景

依頼の成功（得点が入るタイミング）を、Raft のどの時点に対応させるかを決める必要がある。企画書は「単に Raft の Commit 数だけを増やすゲームにはしない。それでは、多数派の島だけに手紙を運ぶことが最適解になってしまう」と述べている。

## 検討した選択肢

### 案 A: Leader で Commit された時点（＝いずれかのノードで最初に適用された時点）

- 長所: Raft の「確定」の定義そのもの。分かりやすい
- 短所: 3 島なら Leader と近い 1 島の間だけで船を往復させれば、どの島の依頼も成功になる。少数派の島に行く理由が満足度しかない

### 案 B: 依頼元の島の台帳に適用された時点

- 長所: 依頼元の島に Commit Index（結果）を届けるまでが仕事になり、少数派の島にも船を出す理由ができる。企画書 §5.4 の「相手から返事が届き、必要な数の島で記録が確認されて初めて、正式な決定が成立する」に、さらに「依頼した住民に結果が伝わる」が加わり、物語としても自然
- 短所: Raft の Commit と、ゲームの「確定」がずれる。プレイヤーに 2 段階（「共和国で確定」と「確定」）を見せる必要がある

### 案 C: 全島で適用された時点

- 長所: 全島を巡る動機が最も強い
- 短所: Raft の過半数の意味が薄れる（「全員に届けないといけない」と誤解させる）

## 決定

案 B。画面では「共和国で確定」（Commit 済み、依頼元は未通知）と「確定」（依頼元に通知済み）を区別して表示する。

## 結果

- 良いこと: 「過半数で決まる（Raft）」と「全島へのサービス（ゲーム）」の両方に価値が生まれる
- 悪いこと: 状態が 1 つ増える。チュートリアル（T7）で説明が必要

## 差し替えるときの影響範囲

`server/internal/game`（状態の判定・スコア）、ゲームデザイン §4.3・§5、進行表（Stage 1 の T7）。

## 見直すきっかけ

- プレイテストで「共和国で確定」と「確定」の違いが理解されないと分かったとき → 案 A に戻し、少数派の島への動機は満足度と公平ボーナスだけで作る
