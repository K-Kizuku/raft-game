## 1. 目的とゴール

### 1.1 プロダクトの目的

日本の離島オープンデータで作った世界の中で、プレイヤーがフェリーを操作して手紙を運ぶ配送パズルゲームを提供する。手紙の正体は本物の Raft（`etcd-io/raft`）が送受信するメッセージであり、**船の運航がそのまま分散合意の成否を左右する**。

### 1.2 成功の定義（ハッカソン時点）

| ID | ゴール | 計測方法 |
|---|---|---|
| G-1 | 3 分のデモ（企画書 §13）を、台本どおりに中断なく実演できる | リハーサルで 3 回連続成功 |
| G-2 | 分散システムを知らない人が、説明なしで Stage 1 をクリアできる | 非エンジニア 3 名のテストプレイで 2 名以上がクリア |
| G-3 | 「船を止めると合意も止まる」ことを、エンジニア画面で示せる | デモで、遮断中は Commit Index が進まない様子を見せる |
| G-4 | 企画書 §15 の検証項目 1〜7 が自動テストで担保されている | CI がグリーン（[§7 検証要件](#7-検証要件企画書-15-の具体化)） |
| G-5 | 実在の離島データ（人口・航路の所要時間・欠航率など）がゲームの難易度に効いている | ステージ定義で、人口が依頼の発生率に、所要時間が航行時間に使われている |

### 1.3 非ゴール（作らないもの）

- 完全なフェリー時刻表の再現、日本全国の全離島の地理的な再現
- 本番用途の分散データベース、Raft のメンバー変更（ConfChange）機能のゲーム化
- 街づくり・経営要素
- アカウント・ランキング・課金（MVP）
- スマートフォン縦画面への最適化（MVP）

## 2. 想定ユーザーと利用シーン

| ペルソナ | 利用シーン | 主に使う機能 | 優先 |
|---|---|---|---|
| U1 カジュアルゲーマー | ハッカソン会場・SNS 経由で 1 プレイ（3 分）遊ぶ | 通常画面、チュートリアル、リザルト | P0 |
| U2 パズル好き | スコアを伸ばすため何度も遊ぶ | 一時停止、速度変更、シード固定でのリトライ | P1 |
| U3 プログラミング学習者 | プレイ後に「何が起きていたか」を知りたい | リザルトの解説、手紙の説明、用語集 | P0（簡易）/ P1 |
| U4 バックエンドエンジニア | Raft の内部状態を観察・実験したい | エンジニアモード、トレースのダウンロード、自由実験モード | P0（簡易）/ P1〜P2 |
| U5 デモ担当者（運営側） | 審査員の前で決まった展開を再現したい | デモ用シード、イベントの手動発火、確実に起動する本番環境 | P0 |

**前提条件**: プレイヤーに分散システムの事前知識は一切要求しない。

## 3. スコープ

### 3.1 MVP（P0）に含めるもの

企画書 §14「必須機能」を全て含め、デモ（§13）に必要なため次の点を **MVP に前倒し** する（理由は [A-01](./09-assumptions-and-open-questions.md#a-01)・[A-12](./09-assumptions-and-open-questions.md#a-12)・[A-17](./09-assumptions-and-open-questions.md#a-17)・[A-18](./09-assumptions-and-open-questions.md#a-18)）。

- 船の複数運行（Stage 2 で 2 隻）
- 嵐イベント（航路遮断・復旧）
- 簡易エンジニアパネル（ノード状態の一覧と、手紙の中身の Raft メッセージ表示）
- 速度の切り替え（早送り）
- 手紙の処分・差し替えのアニメーション
- 操作の記録の保存と、コンテナが止まったときの復元
- コストガード（意図しない課金の増加を防ぐ仕組み。[ADR-0018](./adr/0018-cost-guard.md)）

| 区分 | 内容 |
|---|---|
| ステージ | Stage 1「はじめての郵便船」（瀬戸内・3島・1隻）、Stage 2「島から返事が来ない！」（五島列島・3島・2隻・嵐あり）、デモ用ステージ 2 つ（伊豆版がメイン・五島版がサブ） |
| Raft | `etcd-io/raft` による 3 ノード以上のクラスタをサーバー内で起動 |
| 輸送 | Ferry Transport（港キュー・フェリー・配送） |
| 依頼 | 花火の予約（1 つしかない資源）、屋台の出店枠（数に限りがある資源） |
| 画面 | タイトル → ステージ選択 → ゲーム → リザルト |
| インフラ | Cloudflare への本番デプロイ（`raft.kizuku-hackathon.work` と `raft-demo.kizuku-hackathon.work` の 2 つの Worker）。Cloudflare CLI（`cf`）で管理 |

### 3.2 P1（MVP の後すぐ）

Stage 3（伊豆諸島 6 島。欠航のイベントを含む）、**複数人の協力プレイ**、手紙の積み替え（中継港）、共有予算の依頼、船の故障イベント、注文ラッシュ、漂流瓶、エンジニアモードのフルオーバーレイ、リプレイの再生、R2 でのリプレイの共有、トレースのダウンロード、チュートリアルの強化

### 3.3 P2（将来）

Stage 4、自由実験モード、自動航路設定、複数人協力プレイ、実データからのステージ自動生成、CRDT/Gossip モード、モバイル対応、ランキング

## 4. 機能要件

### 4.1 ゲーム進行（FR-GAME）

| ID | 要件 | 優先 | 受け入れ基準 |
|---|---|---|---|
| FR-GAME-01 | ステージを選んでラウンドを開始できる | P0 | ステージ選択画面でステージを選ぶと、新しいセッション（Durable Object）が作られ、コンテナの起動が始まる。ステージ紹介の間に起動を終える |
| FR-GAME-02 | ラウンドは「開会式 → 航行 → 終了 → リザルト」の順に進む | P0 | [05-game-progression.md §2](./05-game-progression.md) の状態遷移どおりに動く |
| FR-GAME-03 | ラウンドには制限時間がある（ステージごとに 180〜240 秒。デモ用は 120 秒） | P0 | 残り時間が 0 になると操作できなくなり、リザルトへ進む |
| FR-GAME-04 | 一時停止・再開ができる | P0 | 一時停止中はゲーム内時間・Raft の tick・船の移動が全て止まる |
| FR-GAME-05 | ゲーム速度を 0.5x / 1x / 2x / 4x に切り替えられる（デモ操作では 8x と「次の到着・出来事まで進める」も使える） | **P0** | 速度を変えても、同じ操作なら同じ結果になる（決定性は保たれる） |
| FR-GAME-06 | 同じシードでリトライできる | P1 | リザルト画面の「同じ条件でもう一度」で、同じ依頼・イベント列が再現される |
| FR-GAME-07 | 通信が切れるとゲームは自動で一時停止し、5 分以内なら再接続で再開できる（再読み込み・タブを閉じたあとの再開は対象外。セッションのトークンを保存領域に置かないため、[DesignDoc §13.6](./03-design-doc.md)） | P1 | 通信が切れてから 5 分以内に再接続すると、切断前の状態から続けられる。再読み込み・タブを閉じたあとは再開できない（ラウンドの状態は消え、ステージ選択に戻る。仕様） |
| FR-GAME-09 | コンテナが止まっても、操作の記録から再計算してゲームを復元できる | P0 | コンテナを強制的に止めても、一時停止した状態で同じ局面から再開できる（[ADR-0017](./adr/0017-persist-input-log-in-durable-object.md)） |
| FR-GAME-08 | ステージをクリアすると次のステージが解放される（解放状態はブラウザに保存） | P1 | localStorage に保存される |

### 4.2 フェリー操作（FR-FERRY）

| ID | 要件 | 優先 | 受け入れ基準 |
|---|---|---|---|
| FR-FERRY-01 | 港に止まっている船を選び、航路で隣り合う島を行き先に指定して出航できる | P0 | 出航すると、航行時間後に行き先の島に着く |
| FR-FERRY-02 | 船が港にいる間、港に溜まっている手紙を積載量の範囲で選んで積める（ドラッグ＆ドロップとクリック） | P0 | 積載量を超えて積もうとすると拒否される |
| FR-FERRY-03 | 「おまかせ積み込み」で、行き先宛ての手紙を優先度順に自動で積める | P0 | 優先度は [04-game-design.md §3.4](./04-game-design.md) の規則に従う |
| FR-FERRY-04 | 船が島に着くと、その島宛ての手紙が自動で配達され、その島の Raft ノードに入力される | P0 | 配達した手紙の数だけ `RawNode.Step` が呼ばれる |
| FR-FERRY-05 | 宛先が別の島の手紙は、船に積んだまま次の航海で運べる（経由輸送） | P0 | A→B→C と航行すると、C 宛ての手紙が C で配達される |
| FR-FERRY-06 | 船の積み荷を港に降ろして預け、別の船で運び直せる（積み替え） | P1 | 預けた手紙は、宛先に着くまで Raft では処理されない |
| FR-FERRY-07 | 港での停泊（積み下ろし）に一定の時間がかかる（既定 1.5 秒） | P0 | 着いてから停泊時間が終わるまでは出航できない |
| FR-FERRY-08 | 航行中の船の位置・到着予定時刻が表示される | P0 | 画面上で船が航路に沿ってなめらかに動く |
| FR-FERRY-09 | 寄港地を最大 3 つまで予約できる（自動航路） | P2 | — |

### 4.3 手紙と配送（FR-MAIL）

| ID | 要件 | 優先 | 受け入れ基準 |
|---|---|---|---|
| FR-MAIL-01 | Raft が出力したメッセージ（`Ready.Messages`）は、送信元の島の港キューに「手紙」として置かれる | P0 | メッセージ 1 通が手紙 1 通になる。内容は変更しない |
| FR-MAIL-02 | 手紙はゲーム向けの名前・色・形で表示される（[04-game-design.md §2](./04-game-design.md)） | P0 | 色だけに頼らず、形でも区別できる |
| FR-MAIL-03 | 港キューの手紙が増え続けないよう、上限と合流（同じ種類の古い手紙を新しい手紙で置き換える）の規則を設ける | P0 | 港キューは上限を超えない（[§7 V-7](#7-検証要件企画書-15-の具体化)） |
| FR-MAIL-04 | 処分された手紙は港から「海に流れていく」アニメーションで消え、差し替えられた手紙は入れ替わる様子が分かるようにする | **P0** | 手紙が理由なく消えたように見えない（[A-12](./09-assumptions-and-open-questions.md#a-12)） |
| FR-MAIL-05 | 手紙をクリックすると、中身の Raft メッセージ（Type / From / To / Term / Index / LogTerm / Commit / Entries / Reject）を確認できる | P0 | エンジニアパネルで表示される |
| FR-MAIL-06 | 住民の依頼を代表の島へ届ける「依頼書」という手紙がある（Raft メッセージではなく、アプリケーションの手紙） | P0 | [ADR-0008](./adr/0008-application-level-request-forwarding.md) のとおり |

### 4.4 依頼と共有台帳（FR-REQ）

| ID | 要件 | 優先 | 受け入れ基準 |
|---|---|---|---|
| FR-REQ-01 | 各島で、ステージの台本と人口に応じた頻度で住民の依頼が発生する | P0 | 依頼の発生はシードによって決まり、再現できる |
| FR-REQ-02 | 依頼には一意な ID・種類・依頼元の島・期限がある | P0 | — |
| FR-REQ-03 | 依頼は Raft のログに提案（Propose）され、Commit された後、各島の台帳（状態機械）に適用される | P0 | ゲーム側が Commit 結果を勝手に決めない |
| FR-REQ-04 | 花火（1 つしかない資源）は、最初に適用された 1 件だけが成功し、それ以降は「予約失敗」になる | P0 | 二重に確定しない（V-3） |
| FR-REQ-05 | 屋台の出店枠は定員まで成功し、それを超えると「予約失敗」になる | P0 | — |
| FR-REQ-06 | 同じ依頼 ID が何度提案・適用されても、資源の消費は 1 回だけ | P0 | 再送テストで二重に消費されない |
| FR-REQ-07 | 依頼の状態（受付 / 送付待ち / 輸送中 / 審議中 / 共和国で確定 / 確定 / 予約失敗 / 期限切れ）が表示される | P0 | [04-game-design.md §4.3](./04-game-design.md) の状態遷移に従う |
| FR-REQ-08 | 依頼の成功は「依頼元の島の台帳に適用された時点」で判定する | P0 | [ADR-0015](./adr/0015-request-success-judged-at-origin-apply.md) |
| FR-REQ-09 | 依頼元の島は、一定時間（既定 25 秒）内に適用されなければ依頼書を再送する | P0 | 再送しても二重に消費されない |
| FR-REQ-10 | 共有予算からの支払い依頼 | P1 | 残高が足りなければ「予約失敗」 |

### 4.5 イベント（FR-EVT）

| ID | 要件 | 優先 | 受け入れ基準 |
|---|---|---|---|
| FR-EVT-01 | 嵐: 指定した航路を一定時間通れなくする。航行中の船はそのまま進むが、新しく出航できない | P0 | 遮断中はその航路に出航できない |
| FR-EVT-02 | 嵐の予報: 発生の 10 秒前に予告する | P0 | 島のキャラクターから通知が届く |
| FR-EVT-03 | 船の故障: 一定時間、1 隻の船が使えない | P1 | — |
| FR-EVT-04 | 注文ラッシュ: 複数の島で一斉に依頼が発生する | P1 | — |
| FR-EVT-05 | 漂流瓶（古い手紙が届く）: 過去に配達された手紙の複製を、遅れて届ける | P1 | 届いても安全性は壊れない（V-4） |
| FR-EVT-06 | 代表交代の通知: Raft の Leader が替わったら島のキャラクターが知らせる（演出だけで、Raft には介入しない） | P0 | — |
| FR-EVT-07 | デモ用: 発表者のキー操作で、嵐を起こす（D）・8 倍速（Shift+F）・次の出来事まで進める（N）ができる | P0 | `demo` モードでデプロイした Worker（`DEMO_CONTROLS=1`）でだけ使える |
| FR-EVT-08 | 欠航: 計画書の欠航率（利島 17%・御蔵島 41%・青ヶ島 41%）に応じて、その島に接する航路を短時間止める | P1 | 確率はデータから決まり、シードで再現できる（[データ仕様 §4.4](./07-data-spec.md)） |

### 4.6 スコアと勝敗（FR-SCORE）

| ID | 要件 | 優先 | 受け入れ基準 |
|---|---|---|---|
| FR-SCORE-01 | スコアは、依頼の成功・重要な依頼の成功・航行コスト・期限切れ・島の満足度から計算する（式は [04-game-design.md §5](./04-game-design.md)） | P0 | サーバーが計算し、クライアントは表示するだけ |
| FR-SCORE-02 | 島ごとに満足度（0〜100）があり、依頼の成功・期限切れ・長い音信不通で変動する | P0 | 多数派の島だけに運ぶ戦略が最適にならない |
| FR-SCORE-03 | クリア条件は ★1〜★3 の 3 段階。★2 以上（重要な依頼を全て確定）で花火大会の演出が出る | P0 | — |
| FR-SCORE-04 | 失敗しても即ゲームオーバーにはならない | P0 | 制限時間まで遊べる |

### 4.11 コストガード（FR-COST）

[ADR-0018](./adr/0018-cost-guard.md) のとおり。最初からすべて有効にし、G3 以外は管理用 API で再デプロイなしに無効にできる（G5 は再デプロイ）。

|---|---|---|---|
| FR-COST-01 | G1：ゲームごとの見込みの費用を合計し、1 か月 30 USD・1 日 1 USD を超えたら新しいゲームの受付を止める。一般公開とデモ用で共有する | P0 | 上限を超えると `POST /api/sessions` が `503 budget_exhausted` を返し、画面に「本日の受付は終了しました」と出る |
| FR-COST-02 | G2：1 ゲームは最長 30 分で打ち切り、ラウンドの終了でコンテナを止める。1 ゲームで設定できるアラームの回数に上限を設ける | P0 | 30 分でゲームが終わる。アラームの回数の上限を超える設定は拒否される |
| FR-COST-03 | G3：セッション ID に署名を付け、Worker が検証してから Durable Object を呼ぶ。**無効にできない** | P0 | でたらめな ID では Durable Object が作られない（テストで確認） |
| FR-COST-04 | G4：`POST /api/sessions` に Turnstile を通す。Worker で IP ごとのレート制限。ゾーンで 2 つのホスト名に限定した WAF のレート制限と AI クローラーの遮断 | P0 | Turnstile のトークンがない要求は拒否される |
| FR-COST-05 | G5：Worker 1 回あたりの CPU 時間に上限（`limits.cpuMs`） | P0 | 設定ファイルに値がある |
| FR-COST-06 | G6：Cloudflare の予算アラートを 5 USD に設定する。管理用 API で新しいゲームの受付を一括で止められる | P0 | 一括停止すると、新しいゲームが始められない（遊んでいるゲームは続く） |
| FR-COST-07 | 管理用 API（`/api/admin/guards`）で、各仕組みの有効・無効と上限の値を変えられる。`ADMIN_TOKEN` が必要。切り替えの記録を残す | P0 | 再デプロイなしで数秒で反映される |

## 5. 非機能要件

| ID | 区分 | 要件 | 目標値 |
|---|---|---|---|
| NFR-01 | 性能（クライアント） | 7 島・4 隻・手紙 200 通の表示で滑らかに動く | 一般的なノート PC の Chrome で 60fps（最低 30fps）|
| NFR-02 | 性能（応答性） | 操作してから、その結果のイベントが画面に届くまでの時間 | 国内から p95 150ms 以下 |
| NFR-03 | 性能（サーバー） | 1 ゲーム（1 コンテナ）あたりの資源 | 一般公開は `lite`（1/16 vCPU・256 MiB）で、7 島のステージを 4 倍速で動かしても 1 ステップの処理が 50ms に収まること、復元が 3 秒以内に終わることを測って確かめる。足りなければ `standard-1` に上げる（R-02）。デモ用は `standard-1` |
| NFR-04 | 決定性 | （バージョン, ステージ, シード, 入力ログ）が同じなら、トレースは完全に一致する | トレースの SHA-256 が一致する（[ADR-0005](./adr/0005-deterministic-raft-rng-patch.md)） |
| NFR-05 | 正しさ | Raft の安全性に関わる不変条件を、ランダムなシナリオで常に検査する | CI で 1,000 シード以上のシミュレーションテストがグリーン |
| NFR-06 | 可用性 | デモ当日に確実に動く | コンテナが止まっても復元できる（FR-GAME-09）。ロールバック手順（`cf workers deployments`）と、ローカルでのバックアップ起動手順（`make demo-local`）を用意する |
| NFR-07 | セキュリティ | 匿名で使える。悪用を防ぐ | コストガード（FR-COST）、WS メッセージのサイズ上限、Origin の検査、コンテナを外部に直接公開しない（外部への通信も禁止）、シークレットをリポジトリに入れない（公開リポジトリのため） |
| NFR-08 | プライバシー | 個人情報を集めない | Durable Object に保存するのはステージ・シード・操作の記録だけ。Cookie は使わない |
| NFR-09 | 対応ブラウザ | PC の最新版 Chrome / Edge / Safari / Firefox | タブレット横向きは P1、スマートフォンは P2 |
| NFR-10 | アクセシビリティ | 色覚の多様性に配慮する | 手紙の種類は色と形の両方で区別する。文字のコントラスト比 4.5:1 以上 |
| NFR-11 | 言語 | 日本語のみ（MVP） | 文言はキー管理しておき、後から翻訳できるようにする（P2）|
| NFR-12 | 保守性 | ゲームのパラメータはコードではなくステージ定義ファイルで調整できる | パラメータを変えるのにコードの変更が不要 |
| NFR-13 | ライセンス | オープンデータの出典表示と OSS ライセンスの遵守 | このプロジェクトは Apache-2.0（[ADR-0020](./adr/0020-public-repository-apache-license.md)）。クレジット画面・`LICENSE`・`NOTICE`・素材のクレジット（`CREDITS.md`） |
| NFR-14 | 観測性 | サーバーの状態を把握できる | 構造化ログ（JSON）を Cloudflare の Observability に保存し、ダッシュボードで見る（`cf` はリアルタイムのログ表示に未対応） |
| NFR-15 | コスト | 意図しない課金の増加を防ぐ | 基本料金（Workers の有料プラン 月 5 USD）に加える追加料金を、コストガード（FR-COST）で **月 30 USD 以下** に抑える（[ADR-0018](./adr/0018-cost-guard.md)） |

## 7. 検証要件（企画書 §15 の具体化）

| ID | 企画書の検証項目 | 検証方法 | 実装場所 |
|---|---|---|---|
| V-1 | 過半数に到達できないノードでは、新しいログを Commit できない | 分断シナリオのテスト: 少数派側の Commit Index が分断前の値から増えないこと。全シミュレーションで「Commit されたエントリは、Commit した時点で過半数のノードのログにあった」ことを検査 | `server/internal/sim/invariants` |
| V-2 | 通信復旧後、確定済みのログが各ノードで一致する | 各ノードの Applied までのエントリ（index, term, data）が全ノードで一致することを常に検査。復旧後に一定時間待ったら全ノードの Applied が揃うこと | 同上 |
| V-3 | 同じ花火の予約が複数回確定しない | 台帳の不変条件（花火の予約者は最大 1 件、屋台は定員以下）を全ノードの適用ごとに検査 | `server/internal/ledger` |
| V-4 | 古い Term のメッセージが遅れて届いても安全性が壊れない | 漂流瓶（過去のメッセージの複製）を大量に注入するファジング。V-1〜V-3 と「1 つの Term に Leader は最大 1 人」が保たれること | `server/internal/sim` のファジング |
| V-5 | Ready 処理の永続化・送信・適用の順序を守る | Ready ループを 1 関数にまとめ、順序をテストで固定（ストレージへの追記 → HardState の保存 → 送信 → 適用 → Advance） | `server/internal/cluster` |
| V-6 | 同じシード・操作入力で再現できる | 同じ入力ログを 2 回実行し、トレースのハッシュが一致すること。速度を変えた実行とも一致すること | `server/cmd/simcli` + テスト |
| V-7 | 手紙が大量発生しても配送キューが無制限に増大しない | 港キュー・船の積み荷の数に上限がある。どのシナリオでも上限を超えないことを検査 | `server/internal/ferry` |

追加の不変条件（企画書にはないが Raft の正しさに必要なもの）:

- **Election Safety**: 1 つの Term に Leader は最大 1 人
- **Log Matching**: 2 つのノードのログで同じ index・同じ term のエントリがあれば、そこまでのログは同じ
- **単調性**: 各ノードの Term・Commit Index・Applied Index は減らない
