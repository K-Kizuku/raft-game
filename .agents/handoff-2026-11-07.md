## 2. 進め方（ローカル）

### 2.1 ふだんの流れ
`docs/agents/README.md` と `/orchestrate` のとおり。
```bash
scripts/agents/status.sh
go -C tools/agentctl run . plan --repo K-Kizuku/raft-game     # 着手できる Issue と容量（max_workers 5）
scripts/agents/spawn-worker.sh <issue> --background
scripts/agents/review.sh <pr>                                  # まず Codex（CLI）、使えないときだけ Claude
scripts/agents/merge.sh <pr>                                   # Merge Gate が pass のときだけ
scripts/agents/wt.sh cleanup --issue <n>
```

### 2.2 レビュー記録（#85 がマージされるまで）
- Merge Gate の C5〜C8 は、信頼する作者（K-Kizuku）の PR コメント `<!-- agent-review:v1 -->` を読む
- ローカルで Codex の CLI が使えれば、`review.sh` が記録まで投稿する
- GitHub の Codex 連携（PR に `@codex review` とコメント）を使った場合は、結果を **Orchestrator が書き写す**（#89〜#102 で使った形）:
  - `codex-review-state:v1` の `commit_sha` が **PR の HEAD と一致**し、`status: completed` であることを確かめる
  - インラインの指摘は `original_commit_id` で HEAD のものかを見る（`commit_id` は新しいコミットに付け替えられるので使わない）
  - P0→critical、P1→high、P2→medium、P3→low。critical・high が `open` だと C7 で止まる
  - 記録の本文に `@codex` と書かない（Codex が反応して「環境を作れ」とコメントする）
  - 例: PR #100・#99・#95 のコメントの「レビュー記録 — Codex の GitHub 連携の結果の写し」
- **保護されたパス**を変える PR（#98・#85 など）は、`protected_paths_ack: {reviewed: true, weakens_guards: false}` の記録が要る（C12）。Codex の写しでは `reviewed: false` になるので、`review.sh` の代わりのレビュー役（Claude）の記録を使う。**Orchestrator が自分で `reviewed: true` と書かない**

### 2.3 マージは 1 つずつ
- Merge Gate の C10（ベースより遅れていない）があるので、1 つマージするとほかの PR はすべて遅れる
- 手順: main を取り込む（GitHub の「Update branch」か `update_pull_request_branch`）→ **新しい HEAD で** Codex に依頼し直す（古い HEAD の結果を新しい HEAD のものとして書き写さない）→ 記録 → Merge Gate → マージ。1 件 3〜5 分
- 保護されたパスの PR は代わりのレビュー役も要る（10 分ほど）ので、**それを最初にマージする**と、ほかの PR のやり直しが少ない

## 3. クラウドで分かった注意点

### 3.1 ツール・hooks
- **hooks の役割の判定は、セッションのカレントディレクトリで決まる。** Orchestrator が Worktree の中に `cd` すると Worker 扱いになり、`.claude/` への書き込みなどが拒否される。Orchestrator の操作は `cd /path/to/raft-game` してから（別のコマンドで）行う
- **Claude Code は Worker からの `.claude/` への書き込みを拒否する。** `.claude/hooks/**` を変える Issue では、Worker が Worktree の中の `.agents/run/dotclaude/hooks/` に用意し、Orchestrator が内容を変えずに `.claude/hooks/` に写してコミットする（#87 の cf07892・03f4fa1）
- **hooks の agentctl の判定（#87）は字句の安全側。** Worker が agentctl の語（`agentctl`、`go`＋`run`）と書き込みの語（`comment`・`state`・`claim`・`attempt`）を同じコマンドに書くと拒否される。コミットメッセージは `git commit -F <ファイル>` で渡す
- **ワーカーの生存確認は `/proc/<pid>/cwd` で。** Claude Code はプロセスの名前を書き換えるので `pgrep -f` は当てにならない
- **コンテキストの圧縮でバックグラウンドのプロセスが止まることがある**（クラウドで 1 回起きた）。長く動かすワーカーは `setsid nohup` で切り離す。`spawn-worker.sh --background` の実装もこの観点で確かめるとよい
- Worker の Worktree には `web/node_modules` がない。`make test` の web の段は `pnpm install --frozen-lockfile` の後でないと `vitest: not found` で落ちる（Worker が AC を未チェックにしてくる。Orchestrator が同じ HEAD で確かめて記録した: #99・#101）

### 3.2 Issue の書き方（Merge Gate が読む）
- C2: PR の本文の AC は、Issue の AC の文と **完全に一致** させる。補足は AC の行に付け足さず、下の行（`  - …`）に書く
- C11: 「変更予定ファイル」「変更禁止範囲」の箇条書きは、最初のインラインコードが glob として読まれる。**注記は箇条書きにしない**（段落で書く）。禁止の glob が優先する
- Issue の仕様を具体化するときは、補助のエージェントに書かせると速い（#11〜#22 はそうした）。ただし Orchestrator のガードはリポジトリの外への書き込みを拒否するので、置き場所は `.agents/run/issues/<n>-*.md`（gitignore 済み）にし、**GitHub の Issue の本文にも同じものを載せる**（Merge Gate とほかのセッションは GitHub を読む）
- AC に `grep` を書くときは、自分で一度試す（#19 の AC-4 は `rand\.(…|N|…)` が許可した `rand.NewPCG` にも当たっていた）

### 3.3 設計の判断（DesignDoc にまだ反映していないもの）
- **依存の向き `sim` → `cluster`・`ferry`・`ledger` を守るため、`cluster`・`ferry`・`ledger` は `sim` を import しない。**
  - `cluster`: 時刻を持たない。`sim.Engine` が `Process` を呼んだ時点の `Now()` をイベントに付ける（§5 は #101 で直した）
  - `ferry`: 時刻は `int64`（ミリ秒、`SimTime` と同じ値）。`Speed float64` → `SpeedPermille int64`（ステージの `speed: 1.2` を T-201 で `1200` にする）。**DesignDoc §6 は未修正**
  - `ledger`: `Result` に `ReqID`、index の誤りは panic、拒否の理由の一覧、`budget.spend` は `unknown_kind`。**DesignDoc §7.2 は未修正**
  - `cluster` は `ledger` を import せず `StateMachine` 越しに使う。`*ledger.Ledger` を包む `ledgerSM` は T-106 で `sim` に置く
- T-106 の仕様を書く前に、§6・§7.2 の修正を（docs の PR として）まとめて入れるとよい。`SimTime` を末端のパッケージに移す案もある（オーナーと相談）
- 「おまかせ積み込み（`cmd.ferry.autoload`）」の担当のタスクがない。T-106 か別の Issue に割り当てる

### 3.4 Codex のレビューの傾向
- hooks の字句の判定には、毎回新しいすり抜けの形を見つけてくる（引用符・行の継続・`$'...'`・`-o` の値など）。字句の判定には限界があり、最後の砦は Rulesets とレビュー（CLAUDE.md）。直す回数の上限（3 回）で締めた
- 指摘はおおむね妥当だった。安全に関わる P2（#102 のコンテナの名前の正規表現で `rm -f` が広がる）は直してからマージした
